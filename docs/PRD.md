# AM Profile Switch 初期 PRD v0.3.8

**状态**：立项评审稿（QA 已闭环，协议基线已获社区实证）｜ **平台**：Windows 10/11（仅 Win）｜ **负责人**：软件产品
**关联产品**：AM Infinity .97 / AM Infinity .100（鼠标）、BE745 / BD75（键盘，及后续支持板载配置的全部 AM 设备）

---

## 1. 背景与问题

- 鼠标、键盘均支持**板载（onboard）配置**，现有**网页驱动（WebHID）**已能读写并切换配置。
- 游戏用户的真实场景是：**进游戏 → 游戏配置；出游戏 → 日常配置**。目前全靠手动打开网页驱动切换，打断心流，多数人干脆不切。
- 目标：检测前台应用变化，**自动把「鼠标 + 键盘」一起切到该应用对应的板载配置**，用户零操作。
- 社区侧已有旁证：粉丝开源的 am97-cli（Python CLI）完成了 .97 的 HID 协议逆向，动机正是「网页驱动是浏览器独占，鼠标无法参与桌面自动化」[^11^]——自动化需求真实存在，且协议层障碍已被扫清。

## 2. 目标与非目标

### 2.1 目标（MVP）

| # | 目标 | 验收标准 |
|---|------|----------|
| G1 | 前台应用变化时自动切换板载配置 | 前台切换 → 设备生效 ≤ 500ms，无感知输入中断 |
| G2 | 鼠标 + 键盘联动切换 | 一条规则可同时作用于多台在线设备，各设备配置独立指定（两层模型） |
| G3 | 设备缺失/更换不报错 | 任一设备不在线时静默跳过，仅状态提示，不弹窗、不中断其余设备 |
| G4 | 轻量化常驻 | 常驻内存 ≤ 60MB，空闲 CPU ≤ 0.5%，安装包 ≤ 15MB，托盘常驻、开机自启 |
| G5 | 反作弊零风险 | 不注入、不读游戏内存、不 hook 输入，纯用户态 + 仅与自家 HID 配置接口通信 |
| G6 | 失败可观测（遥测） | 切换失败场景 100% 有日志并上报（匿名），游戏 ID 维度可统计，先于售后发现问题 |

### 2.2 非目标（MVP 不做）

- 配置**编辑**（DPI、键位、宏、灯效的编辑仍由网页驱动承担，本工具只发切换指令）
- **手动切换 / 锁定模式**（网页上位机已有此能力，不重复；公测反馈确有需要再议）
- 向设备写入具体参数（只切板载槽位，不碰参数）
- 多 Windows 用户管理（每用户自行启动自己的实例即可）
- macOS / Linux、配置云同步、游戏内 overlay

## 3. 核心用户故事

1. 作为 CS2 玩家，我希望双击 cs2.exe 后，鼠标自动切到游戏配置、键盘切到游戏键位；退出游戏后，一切自动回到默认配置。
2. 作为多设备用户，我桌面上插着 AM Infinity .100 和 BD75，切换时一起变；今天只带了鼠标出门，键盘不在，工具不能报错。
3. 作为新用户，我希望规则列表预置热门游戏，开箱即用，且能「把当前前台程序」一键添加为规则。
4. 作为产品经理，我希望用户切换失败时我**在后台报表里先看到**，而不是等售后工单。
5. （社区实证）作为桌面自动化玩家，我希望设备能被脚本/工具触达——am97-cli 的出现证明这个需求强到用户愿意自己逆向协议 [^11^]。

## 4. 功能需求

### F1 前台应用检测

- 采用 Win32 `SetWinEventHook` 监听 `EVENT_SYSTEM_FOREGROUND`，事件驱动、零轮询——同类工具验证过的标准做法，即时触发且 CPU 开销趋近于零 [^1^][^2^]。**该机制已有编译验证通过的 Rust demo（M0 验证件 #1）**。
- 命中后解析：进程名（exe）、完整路径、窗口标题。
- 管理员权限运行的游戏：前台事件对普通权限进程依然可达；路径读取用 `OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION)` + `QueryFullProcessImageNameW`，失败降级为进程名匹配，**本工具不要求管理员运行**。
- 防抖去重：同一进程连续触发不重复写设备；浏览器标签切换等标题闪烁不触发。
- **持续维护「最近前台程序」历史**（排除自身 exe 与桌面），供添加游戏时选择。关键边界（GUI 评审发现）：用户点「添加游戏」按钮时本工具必然处于前台，直接取「当前前台」必然取到自己——所以取的是**历史里的上一个**，不是当前。

### F2 规则引擎（两层模型）

各设备板载槽位数不一致，因此规则**不能**是「游戏 → 统一槽位号」，而是两层：

- **层级一 · 设备**：这条规则作用于哪些设备（按设备名称）；
- **层级二 · 设备配置**：每台设备各自切到哪个配置（配置存在于设备板载存储中，规则里只引用标识）。

退出游戏（前台不再是任何规则）时，**全部设备一律回落到全局默认配置**——规则不记录任何还原关系（v0.3.2 简化：逐规则 restore 与全局回落并存会让用户无法理解「退出后我处在哪个配置」，消费者心智只需要一句话：**进游戏切配置，出游戏回默认**）。

数据原则：**只存标识引用，不复制任何配置内容**。规则文件只含三类字段：游戏 ID、匹配条件、各设备的目标配置。配置本体永远以设备板载为唯一事实来源，避免双写不一致。

术语纪律（v0.3.2 新增）：**界面只暴露「产品名 + 板载配置名」**；「槽位 / slot」仅是协议层实现细节，不出现在任何消费者可见的文案中。

- ⚠️ **槽位名称风险（v0.3 新增）**：社区实测显示，设备状态接口只暴露槽位**序号**（`profile 0`），未见槽位名读取命令 [^11^]。M0 必须验证「能否从设备或网页驱动数据读到槽位名称」：
  - 能读到 → 规则存配置名，运行时 名称→槽位 解析（原方案）；
  - 读不到 → **降级方案**：规则改存「槽位号 + 用户自定义别名」，UI 允许用户给槽位起名（如「CS2 专用」），名称仅存于本地规则文件。
- 预置热门游戏包（CS2、Valorant、Apex、PUBG、永劫无间、LoL 等 exe 清单），可改可删。**用户删除的预置条目要记 tombstone，预置包更新只新增/修订未删除条目，不得复活**（v0.3.6 新增）。
- **删除规则**（v0.3.6 新增，v0.3.7 修正入口位置）：规则行尾 ✕，常显低透明、悬停高亮，两步确认、不弹窗；预置与自建规则同权可删。**删除正在生效的规则 = 立即回落全局默认配置**——规则消失等价于不再命中，与退出游戏同路径。
- 「添加游戏 / 应用」弹层**只选程序、不配设备**（v0.3.3 简化：设备配置若同时出现在弹层和规则行，就是同一功能两个入口；配置只在规则行完成）。三层来源保证冷启动也不落空（GUI 评审发现：刚装完、前台历史为空时，不能要求用户"先开一把游戏再回来配"）：
  1. **预置规则包**开箱即用——热门游戏不需要任何添加动作，消化冷启动的大多数场景；
  2. **最近前台历史**默认选中上一个、可改选（历史由 F1 事件流维护，排除自身）——非预置游戏的热路径；
  3. **手动选择 exe**（Win32 GetOpenFileName，.exe 过滤）——永不落空的兜底，游戏没运行过也能配。
- 新规则出生时**全部设备指向默认配置**，用户在规则行里逐设备改选；配置列表实时读自设备板载供选择，杜绝手填。**修改正在生效的规则时，对应设备立即补切**（所见即所得，不用退出游戏重进）。
- **添加查重**（v0.3.4 新增）：以 exe 文件名（不区分大小写，Windows 文件系统语义）为规则唯一身份，一个 exe 至多属于一条规则，预置包同样参与查重。两层防重：
  1. **选择时预防**——历史列表 / 手动选中的程序若已被规则覆盖，标记「已添加」，主按钮变为「查看规则」；
  2. **保存时兜底**——命中已有规则则不新建、不报错，直接定位并高亮该规则（用户意图是"配置这个程序"，带他去已有规则即是正解）。
  已知边界（MVP 不处理，FAQ 覆盖）：同名 exe 的不同程序无法区分（匹配本身就按 exe 名）；同一程序的启动器/本体多 exe 合并到一条规则（schema 的 match 已是数组，合并 UI 留待后续版本）。
- （后续版本可选增强：「正在运行的进程」列表、扫描 Steam/Epic 已安装游戏库——属体验优化，非 MVP。）
- 存储：`%APPDATA%/AM/app-switch/rules.json`（schema 见 §6）。

### F3 设备管理（容错核心）

- 范围控制：**只对支持板载配置的设备生效**（受支持型号清单：AM Infinity .97 / .100、BE745、BD75 及后续型号）。不支持的设备不出现在设备台账中，不做任何通信。
- 枚举参数（社区实证基线 [^11^]）：

| 参数 | 值 | 说明 |
|------|-----|------|
| VID | `0x0E8D` | 主 VID |
| PID（2.4G 接收器） | `0x0703` | .97 的 dongle；.100 与键盘的 PID 待 M0 枚举确认 |
| PID（鼠标注线直连） | `0x0880` | 另有备选 ID 对 `(0x35A1, 0x0035)` 出现在真实设备上，枚举时需兼容 |
| Usage Page | `0xFF13` | 厂商自定义集合，配置通道所在 |
| Feature Report | `0x14` | 命令与回包共用 |

- **拓扑建模（v0.3 新增）**：鼠标经 dongle 连接时，通信入口是 dongle，鼠标是 relay 目标（`device_id = 0x80`）；线缆直连时 `device_id = 0x00`。DeviceManager 需同时发现两条路径并优先 dongle（社区实现同样 dongle 优先 [^11^]）。键盘 BE745/BD75 的连接拓扑 M0 待验。
- 热插拔：`RegisterDeviceNotification`（HID 类 GUID）+ `WM_DEVICECHANGE`，设备路径级过滤；移除即关句柄、标记 offline [^3^][^4^]。
- 能力读取：设备接入时**瞬态**读取型号、固件版本、槽位清单后**立即释放句柄**（见 F4 瞬态连接）。
- 设备状态展示**并入状态页**（设备 / 当前配置 / 在线情况一屏看全，v0.3.2 起不单设「设备」页签）。

### F4 切换执行（协议基线已实证）

- **协议基线（社区逆向 + WebHID 抓包交叉验证 [^11^]，M0 实测复核）**：

```
[payload_len][device_id] [05][type][len_lo][len_hi][cmd_lo][cmd_hi][data...]
```

- `device_id`：`0x00` = 当前连接的设备本体；`0x80` = 经 dongle relay 寻址鼠标
- `type`：`0x5A` 命令 / `0x5B` 回复 / `0x5D` 写确认
- payload 零填充至 61 字节，承载于 Feature Report `0x14`
- **忙等待与回包解析**：设备忙时返回零长度帧，需轮询（社区实现：30ms × 最多 40 次）；一次读取可能堆叠多条响应，需按帧走到 cmd id 匹配为止 [^11^]

- **指令白名单（v0.3 收紧，只允许这三类）**：

| 命令 | ID | 用途 | 社区验证状态 [^11^] |
|------|-----|------|---------------------|
| `getProfile` | 12489 | 读当前槽位 | ✅ 真机实测 |
| `changeProfile` | 12488 | **切槽位（本工具唯一写操作）** | ⚠️ 转录自官方 JS，未实测 —— **M0 第一验证项** |
| 固件版本/设备信息读取 | M0 确认 | 特性门控 | —— |

- **破坏性命令黑名单（硬编码进发送路径兜底拒绝，来源 [^11^]）**：

| ID | 命令 | 危害 |
|-----|------|------|
| 12494 | `resetSettings` | 清空全部配置 |
| 12395 | `clearBonded` | 毁掉 2.4G 配对 |
| 12394 | `setPairingUniaa` | 配对握手 |
| 4353 | `rebootPairingDevice` | 断链重启 |

- **瞬态连接策略（v0.3 重要修正）**：社区实测确认浏览器打开网页驱动时会**独占设备句柄**，第三方工具打开会失败并提示「关闭网页驱动页签」[^11^]。反过来说，我们 24/7 常驻若一直持有句柄，**网页驱动同样会被我们挡死**。因此：
  - 平时**不持有**任何设备句柄；
  - 切换瞬间才 open → changeProfile → getProfile 读回校验 → close，单次占用 < 200ms；
  - 打开失败（被网页驱动占用）→ 延迟重试 ≤ 2 次 → 仍失败按设备标记「忙」，记日志 + 遥测，不弹窗。
- 多设备并行下发，单设备失败不阻塞其他设备。
- 冲突提示：连续失败后温和提示「请关闭网页驱动中的该设备页签」。

### F5 遥测（MVP 内置）

目的：**先于售后发现问题**——切换失败不能靠用户主动反馈。

- **失败事件全量上报**，成功事件聚合计数（按 游戏 ID × 设备 计次数），控制量级。
- 失败事件载荷：

```json
{
  "event": "switch_fail",
  "game_id": "cs2",
  "device": "AM Infinity .100",
  "target_profile": "Gaming",
  "error_code": "WRITE_TIMEOUT",
  "retries": 2,
  "latency_ms": 480,
  "fw_version": "1.2.3",
  "app_version": "0.1.0",
  "install_id": "随机UUID"
}
```

- 错误码枚举（v0.3 扩充）：`WRITE_TIMEOUT` / `DEVICE_BUSY`（被网页驱动占用）/ `DEVICE_OFFLINE` / `PROFILE_NOT_FOUND` / `VERIFY_MISMATCH`（读回校验不一致）/ `PROTOCOL_ERROR`（回包帧解析异常）。
- 隐私红线：`install_id` 为首次启动随机生成的 UUID，不含硬件 ID / 账号信息；只收游戏 ID（exe 名），**不收**窗口标题、路径、使用时长。首次启动告知 + 设置中可关闭。
- 本地日志：最近 100 条切换记录，便于社区反馈排查。

### F6 状态与反馈

- 托盘图标三态：运行中 / 有设备离线（信息性角标）/ 有设备切换失败（警示角标）。
- 信息架构（GUI 交互稿 v0.2 起）：页签顺序 = 动手频率——**规则（默认首页）/ 状态 / 设置**。规则页是消费者唯一需要动手的页面；状态页回答「它在工作吗」，上半部分（一句话状态 + 流水线 + 设备清单）面向消费者，日志区面向测试与支持。
- **rules.json 不向消费者展示**；诊断价值由设置页「复制诊断信息」按钮承担（规则 + 设备/固件版本 + 最近日志一键复制，供社区测试反馈与售后排障），自动发现仍由遥测兜底。
- 状态页顶部为消费者准备一句话状态：「待命 · 全部设备处于默认配置」/「「XX」规则生效中 · 退出后自动回默认」。
- 托盘菜单 MVP 仅保留：打开面板、退出。（手动切换与锁定不在 MVP，见 §2.2）

## 5. 技术选型

### 5.1 框架对比

| 维度 | **Tauri 2.x（推荐）** | Electron | WinUI 3 / WPF | Rust + Slint 纯原生 |
|------|----------------------|----------|---------------|---------------------|
| 安装包 | 3–10MB [^6^] | 85–250MB [^6^] | 中等（依赖 .NET 运行时） | 最小 |
| 常驻内存 | 空闲约 30–50MB，比 Electron 低 58–75% [^6^][^7^] | 100–300MB [^6^][^7^] | 中等 | 最低（~10MB） |
| 空闲 CPU | < 0.5% [^6^] | 1–5% [^6^] | 低 | 极低 |
| 复用网页驱动前端 | ✅ 直接复用（WebView2 渲染） | ✅ 复用 | ❌ 重写 XAML | ❌ 重写 |
| HID/系统 API | Rust：hidapi + windows-rs，生态成熟 | node-hid 原生模块，分发麻烦 | C# P/Invoke，成熟 | 同 Tauri |
| 自动更新 | 内置（增量）[^6^] | electron-updater | 需自建 | 需自建 |

**结论：Tauri 2.x。** 决定性理由：
1. 轻量化是硬指标（游戏用户对常驻进程资源占用极度敏感）；
2. 网页驱动前端 UI 可直接搬进 WebView2，开发量最小；
3. Rust 侧只需三个薄模块（前台检测 / HID 通信 / 规则引擎），hidapi crate 在 Windows 下免驱动、免安装——社区已用 Python hidapi 绑定在同一设备上跑通，Rust hidapi 底层同为 libusb hidapi，API 一一对应 [^11^]。

### 5.2 架构（独立 App，为并入 AM Master 预留边界）

```
┌──────────────────────────── Tauri App ────────────────────────────┐
│  WebView2 UI（复用网页驱动前端技术栈）                              │
│    · 规则管理 / 设备台账 / 切换历史 / 设置                          │
│        │  tauri.invoke / event                                     │
│  am-profile-switch-core（独立 Rust crate，可迁入 AM Master）        │
│    ├─ ForegroundMonitor   SetWinEventHook(EVENT_SYSTEM_FOREGROUND)│
│    │                      【M0 验证件 #1 已完成编译验证】           │
│    ├─ DeviceManager       hidapi 枚举 + WM_DEVICECHANGE 热插拔     │
│    │                      + dongle relay 拓扑（0x00/0x80）          │
│    ├─ HidProtocol         帧编解码 + 忙等待轮询 + 堆叠帧解析        │
│    │                      + 命令白名单/黑名单（§4 F4）              │
│    ├─ RuleEngine          rules.json 两层规则匹配、还原回落        │
│    ├─ SwitchOrchestrator  瞬态连接、并行下发、重试、读回校验        │
│    └─ Telemetry           失败全量 / 成功聚合，匿名上报            │
└───────────────────────────────────────────────────────────────────┘
```

两条架构纪律：
1. **切换链路全部在 Rust core**，UI 冻结/崩溃不影响核心，UI 只是观察者；
2. **core 做成独立 crate、零 Tauri 依赖**，公测验证、口碑达标后并入 AM Master 时是「搬库」而不是「重写」。

### 5.3 反作弊与安全红线

现代反作弊（Vanguard / EAC / BattlEye / Ricochet）检测的是进程注入、内存读写、可疑驱动、输入自动化 [^8^]。本工具四样都不碰：纯用户态进程，只通过标准 HID API 向自家设备的**配置接口**发 Feature Report。同类纯外部工具在 Vanguard/EAC/BattlEye 下长期无冲突先例 [^9^]；反作弊不直接盯 USB HID 输入流也是公开共识 [^10^]。

红线清单（写进开发规范）：
- ❌ 不 OpenProcess 游戏进程做任何读写
- ❌ 不装内核驱动、不用 interception 类驱动
- ❌ 不做全局低级键鼠 hook（MVP 无热键需求，天然规避）
- ❌ **禁止枚举/扫描 HID 命令 ID**（v0.3 新增）：该协议族命令 ID 为扁平空间，读、写、破坏性操作混杂且字节层面无法区分；社区开发者扫描 256 个 ID 范围时意外触发 `clearBonded`，真实丢失了配对与全部配置 [^11^]。发送路径只允许白名单命令，黑名单硬编码兜底拒绝
- ❌ 不引入 `raw` 任意命令发送能力（社区 CLI 有 `am97 raw`，我们不给用户这个枪口）
- ✅ 发布前代码签名（EV 证书），降低杀软误报
- ✅ 官网挂「反作弊兼容性说明」页，列明技术原理

- NSIS/MSI 安装包（Tauri 内置产出）+ 内置增量自动更新 [^6^]

## 6. 数据模型（rules.json）

只存标识引用，不复制配置内容（v0.3 兼容「槽位名」与「槽位号+别名」两种形态，取决于 M0 验证结果）：

```json
{
  "version": 2,
  "rules": [
    {
      "game_id": "cs2",
      "match": ["cs2.exe"],
      "apply": [
        { "device": "AM Infinity .100", "slot": 2, "alias": "游戏" },
        { "device": "BD75", "slot": 1, "alias": "游戏" }
      ]
    }
  ]
}
```

- `game_id`：稳定标识（预置包统一命名），遥测同口径；
- `apply`：两层模型的落盘形式——设备层 + 配置层；**无 restore 字段**：退出游戏一律回落全局默认配置（每台设备的 0 号配置）；
- `slot` 为运行时实际发送的槽位号，`alias` 为本地显示名（若 M0 验证设备可读槽位名，则 alias 自动同步为设备名）；
- 某 `device` 当前不在线 → 静默跳过该条，其余设备照常执行。

## 7. 容错设计明细

| 场景 | 行为 |
|------|------|
| 键盘不在线、鼠标在线 | 只切鼠标，台账中键盘显示「离线」，无弹窗 |
| 全部设备离线 | 规则照常匹配，台账全灰，托盘 tooltip「等待设备接入」，接入后自动补切 |
| 切换中途设备被拔出 | `DBT_DEVICEREMOVECOMPLETE` 关句柄，本次写入作废，记日志，不重试风暴 |
| 规则中的槽位在设备上不存在 | 跳过该设备，台账提示「配置不存在」，遥测 `PROFILE_NOT_FOUND` |
| 写入错误/超时（含设备忙零长度帧超限） | 重试 ≤ 2 次 → 标记失败 → 托盘角标 + 日志 + 遥测 `WRITE_TIMEOUT` |
| 设备被网页驱动占用（社区实证 [^11^]） | 瞬态连接使冲突窗口 < 200ms；仍撞车则延迟重试，连续失败提示「请关闭网页驱动页签」，遥测 `DEVICE_BUSY` |
| 读回校验与目标槽位不一致 | 重试 1 次，仍不一致标记失败，遥测 `VERIFY_MISMATCH` |
| 设备不在受支持清单 | 不枚举、不通信、不出现在台账 |
| 固件版本不支持槽位切换指令 | 台账显示「需升级固件」+ 链接升级页，遥测记录固件分布 |
| 鼠标经 dongle 但 dongle 不在、插线直连 | DeviceManager 自动切换 0x80/0x00 寻址路径，用户无感知 |

## 9. QA 记录

| # | 问题 | 结论 |
|---|------|------|
| 1 | 切换语义？ | 只对支持板载配置的设备做**槽位切换**（changeProfile），Host 不控制具体参数 |
| 2 | 槽位数不一致怎么办？ | 两层规则模型（游戏 → 设备 → 槽位），运行时按各设备实际清单解析，见 F2/§6 |
| 3 | 数据存什么？ | 只存设备名称、配置标识、游戏 ID，不复制配置文件；v0.3.2 起取消逐规则还原字段，退出一律回落全局默认配置 |
| 4 | 产品归属？ | 独立 App 先行、资源消耗最小；core 独立成 crate，公测好评后并入 AM Master |
| 5 | 多 Win 用户？ | 不处理，每用户自行启动 |
| 6 | 遥测？ | MVP 内置：游戏 ID 维度统计 + 切换失败全量日志，匿名、可关闭 |
| 7 | 槽位名称可读吗？（v0.3 新增） | 社区实证状态接口只有槽位序号 [^11^]；M0 验证，读不到则用「槽位号 + 本地别名」降级方案 |
| 8 | 添加弹层里要配设备吗？（v0.3.3 新增） | 不配。弹层只选程序；设备切到什么只在规则行设置——同一功能不出现在两个页面，消费者只需学会一个地方 |
| 9 | 用户添加的 app 要查重吗？（v0.3.4 新增） | 要。exe 文件名（不区分大小写）即规则身份，一个 exe 至多一条规则；选择时标「已添加」并把按钮变为「查看规则」，保存时兜底再查、命中直接定位已有规则不新建 |
| 10 | 规则能删吗？预置规则删了会被更新加回来吗？（v0.3.6 新增） | 能删，预置/自建同权；行尾 ✕ 两步确认、不弹窗；删除正在生效的规则立即回落默认。预置包更新不得复活已删条目——删除即记 tombstone |

## 10. 社区生态策略（v0.3.1 修订）

am97-cli 对我们的价值是**协议情报**，不是代码资产：帧格式、命令 ID、黑名单、忙等待机制已吸收进 §4 F4，它的使命到此为止。**我们不集成它、不依赖它、也不自己做 CLI**——前台检测与协议发送天然在同一个进程里（社区源码证明发命令的核心逻辑只有百行级），拆出 CLI 只会多一个要分发、签名、维护的产物。

保留的只有最低成本的社区动作：

1. **鸣谢与邀请**：发布物料致谢 am97-cli 作者 TheMasterDingo，M2 公测优先邀请——现成的种子用户 + 最好的协议 review 者；
2. **不重复造轮子**：脚本化/桌面自动化需求已由社区作品覆盖（MIT 协议），我们聚焦自动切换主场景，不与社区正面重叠；未来该需求若大到值得官方介入，优先走支持/收编路径而非替代。
